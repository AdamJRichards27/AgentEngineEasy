# AgentEngineEasy — Phase 3 Capability Matrix & Pilot Readiness Trace

**Scope of this document.** Evidence-backed capability matrix plus three end-to-end scenario traces for AgentEngineEasy ("Agent Engine 2.0"), produced to support a go/no-go decision on a small controlled pilot (5–10 invited agents, synthetic/test data only, no public signup, no live customer money) running on the codebase exactly as it stands in this mirror.

**Method.** Every claim below is grounded in a file:line citation read directly from `/home/claude/work/AgentEngineEasy`. Where a claim needed empirical (not just static) confirmation, the automated test suite was run locally against a real, freshly-initialized PostgreSQL 16 database:

- `packages/db`: migrations `0000`…`0009_flimsy_norrin_radd` applied cleanly via the documented runner (`pnpm --filter @aee/db run db:migrate`, `packages/db/src/migrate.ts`) to a disposable database — verified the resulting schema (94 tables, including `session_epoch` on `users` and all `integration_*` tables).
- `packages/events`: **63/63 tests passing** (`pnpm --filter @aee/events run test`).
- `apps/api`: **662/662 tests passing, 1 explicitly-documented placeholder skipped, 0 failures** — the full suite behind `pnpm --filter @aee/api run test` (663 tests / 82 suites across `routes/__tests__`, `lib/**/__tests__`, `middlewares/__tests__`), including `routes/__tests__/runTransactionVerticalSlice.test.ts`, the one true first-created-account-through-closed-transaction end-to-end test.

Where I could not verify something (no route, no test, code silent), I say so explicitly rather than guessing.

## 3. SCENARIO B — operational exceptions

## 5. Key gaps for a controlled pilot

Ordered roughly by how directly each would bite during a 5–10-agent pilot:

1. **No real invitation/authentication.** `dev-login` is passwordless and self-serve; running the pilot at all requires enabling it (`ALLOW_DEV_AUTH=true`). Anyone who knows (or guesses) a pilot brokerage's exact name string can join it as a full Agent with no approval step. Mitigate operationally: treat the brokerage name as a shared secret for the pilot's duration, and manually audit the user list (`GET /auth/known-users`, itself only reachable with the same flag) periodically. *(`apps/api/src/routes/auth.ts:30-135`)*
2. **No in-app user lifecycle management.** Granting/changing a role (including the Pit Crew role itself), deactivating a departed agent, and recovering from a brokerage losing its only Brokerage Administrator all require a direct database write by engineering — none of this has a route, a UI, or an audit trail of its own. This is the single biggest *operational* (not security) gap for running a live pilot smoothly. *(no `db.update(users)…role` or `isActive: false` outside test helpers)*
3. **No real outbound communications.** Every email/SMS in this build is a sandboxed no-op labelled `sandbox_email`/`sandbox_sms`. If the pilot plan assumes agents or synthetic "parties" will actually receive a real notification, that capability does not exist today. *(`apps/api/src/lib/communications/providers/sandboxEmail.ts`, `sandboxSms.ts`)*
4. **No real AML/CTF or e-signature vendor.** Both are mock providers by default with no named real vendor integrated (e-sign's own adapter comment: "vendor TBD"). Fine for rehearsing the workflow with synthetic data (which is the pilot's stated constraint) — but the pilot must not be described internally or externally as having exercised real compliance checks or legally-binding signatures.
5. **No transaction cancellation / fall-through state.** A deal that dies (not just stalls) — the most common real-world exception in property transactions — has no system state to land in. A pilot agent whose deal genuinely falls through will have a permanently-stuck transaction with no clean way to record that outcome or free the property for a new buyer.
6. **Financial disputes can be opened but never formally closed** through the app once a provider reports one — only manageable via direct DB intervention today.
7. **AI is Copilot-only.** The other four planned AI roles (including "Business Coach," the closest analogue to "AI coaching") are architected but literally throw `not implemented in this build` if ever invoked — there is nothing to pilot there beyond a read-only Q&A widget.
8. **Minor hygiene items, not blockers:** three orphaned migration files (`0009_tired_warbird.sql`, `0010_integration_and_data_exchange_foundation.sql`, `0011_session_epoch_revocation.sql`) exist on disk but are not referenced by `packages/db/migrations/meta/_journal.json` — verified empirically that the migration runner still produces a correct, complete schema (their content was fully folded into `0009_flimsy_norrin_radd.sql`, which *is* in the journal), so this is dead clutter rather than a missing-migration risk, but it could confuse a future engineer who tries to hand-apply the orphaned files. Separately, `packages/db/src/schema/financial.ts:673-699`'s code comment claims a specific unique index "NOT YET APPLIED AS A MIGRATION" — verified this is now stale documentation; the index exists and was confirmed present after migration.

## What this codebase does well (for balance)

The engineering discipline on display — real transactional locking for concurrent-offer races, append-only audit history for date changes, idempotency chokepoints with DB-level uniqueness backstops on every financial mutation, tenant-isolation checks joined into the same query rather than bolted on after the fetch, a self-correcting exception-engine catalogue that even watches for contradictions in its own forced-override path, and a 662/662-passing test suite that includes one genuine full-stack HTTP end-to-end test of the entire Run-tier lifecycle — is well above what "partially built" would suggest for the Run tier specifically. The gaps identified above are real and should inform the go/no-go decision, but they are gaps in *scope* (features not yet built, or deliberately mocked pending a real vendor) rather than evidence of an unreliable foundation for the parts that are built.
