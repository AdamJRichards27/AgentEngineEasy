## 5. Existing PR #16 architecture summary

The Communications Hub (merged via PR #16, head `a34461a3954b65cc30b67dd7de5dfd49df2afc5b`) is a property-centred, append-history communications system: `communicationThreads` (one per property + topic) contain `communicationMessages` (draft/sent/received), addressed to `communicationParticipants` resolved from the canonical `parties` table wherever possible. Delivery state is tracked via an append-only `communicationDeliveryAttempts` ledger while `communicationMessages.status` holds the latest denormalised state. Sends go through a durable outbox (`outbox.ts`) with a `communicationConsent` gate, `communicationCostLedger` cost control, quiet-hours enforcement, and versioned `communicationTemplates`. Inbound provider events land in `communicationWebhookEvents` with signature verification and `(provider, providerEventId)` idempotency. Every table before Priority 3 required a non-null `propertyId`.

## 6. Contact-first architecture

Grow's Contact 360 is person-first and property-optional, so Priority 3 extends the same tables rather than building a parallel model: both `communicationThreads` and `communicationMessages` gained a nullable `partyId` anchor alongside an now-nullable `propertyId`, with a DB-level CHECK constraint guaranteeing at least one anchor is always present. A contact-first thread is created via new routes (`/grow/contacts/:partyId/communications/...`) but flows through the exact same service functions (`createThread`, `createDraftMessage`, the outbox, consent, cost control, templates, webhooks) as a property-first thread — no second thread/message model, no new Grow-specific communications tables, no parallel send pipeline.

## 7. Schema changes

Migration `0015_productive_morph.sql` (generated by a real `drizzle-kit generate` run against the edited schema, not hand-authored):
- `communication_messages`/`communication_threads`: `property_id` — dropped NOT NULL.
- Both tables: new nullable `party_id integer references parties(id)`.
- Both tables: new index on `party_id`.
- Both tables: new CHECK constraint `property_id IS NOT NULL OR party_id IS NOT NULL`.

This mirrors the precedent already set by `grow_relationships.property_id` (migration `0013_grow_relationship_property_optional.sql`). **Known limitation — see §22**: the migration SQL and the updated `_journal.json` are committed and confirmed correct by real CI (the "Deterministic clean-database migration check" step passes), but the accompanying `migrations/meta/0015_snapshot.json` (drizzle's ~457KB full-schema snapshot, required byte-for-byte by CI's "Schema drift check") is not present on the branch as a single committed file, and an unrelated side effect of the interim transport workaround is now actively making that specific check report a false PASS — see §22 for full detail; **do not treat the Schema drift check's current green status as real evidence of no drift.**

## 8. Existing property-flow regression result

Every property-first code path was read in full and confirmed unchanged in behaviour: thread creation still accepts a `propertyId`-only body exactly as before; `createDraftMessage` denormalises `propertyId`/`partyId` from the parent thread rather than trusting caller input, so a property-only thread continues to produce property-only messages; the brokerage-wide hub feed's `innerJoin` on `properties` was changed to a `leftJoin` (needed so contact-first messages appear at all) which returns identical rows for property-anchored data, since the joined key is always present there; consent, cost-control, quiet-hours, templates, and settings logic needed zero changes. A new regression test (`communications.test.ts`) asserts a property-first thread and message keep `propertyId` set and `partyId` null throughout create→send. This is now additionally confirmed by a real, full green run of the API automated test suite (run #281, §21), not only by source reading.

## 9. Contact 360 integration

Backend: three new routes on the existing `communicationsRouter` — `POST /grow/contacts/:partyId/communications/threads` (creates a contact-anchored thread, `grow.contacts.manage`), `GET /grow/contacts/:partyId/communications/threads` (`grow.contacts.read`), `GET /grow/contacts/:partyId/communications/recipients` (`grow.contacts.read`, returns the party's own email/mobile as a send candidate). Everything downstream (adding a participant, drafting, approving, sending) reuses the Hub's existing thread-scoped routes unchanged. Frontend: a new `ContactCommunicationsSection` component on the Contact 360 page offers Email/SMS quick-start (creates a contact-first thread, adds the contact as its one participant, opens the existing composer pre-selected) and a thread/message list that doubles as that contact's communications history. The existing composer (`ComposerForm`) and thread-detail/participant UI were generalised to take a recipient source instead of a hardcoded `propertyId`, rather than being duplicated.

## 10. Relationship Timeline integration

`relationshipTimeline.ts` gained a `"communication"` source: `buildCommunicationEvent` maps one `communicationMessages` row to at most one `GROW_TIMELINE_EVENT_TYPES` entry (`EMAIL_SENT`/`EMAIL_DELIVERED`/`EMAIL_FAILED`/`EMAIL_RECEIVED` and the SMS equivalents), sourced by two live queries — direct `partyId` match for contact-first messages, and a `communicationParticipants`-mediated, tenant-reverified lookup for property-first threads where the contact is a participant — merged and deduplicated by message id. Because `communicationMessages.status` is a single denormalised "latest state" column, a message's SENT→DELIVERED transition simply changes which one event that message produces, never emitting two: no copy into a new Grow table, the Hub tables remain the sole source of truth. `EMAIL_OPENED` stays unpopulated (no open-tracking column exists yet, unchanged from Priority 2).

## 11. Grow Today integration

`GrowTodayAction` gained `contactEmail`/`contactMobile` (sourced from the same `parties` join each Grow Today query already performs), and `GrowTodayActionButton`'s kind union gained `"email" | "sms" | "view_contact"`, populated additively alongside existing buttons in `apps/api/src/lib/growToday.ts`. No ranking, Do Now/Do Today/Keep Warm, 21-day threshold, deduplication, or opportunity-prioritisation logic was touched. Frontend `GrowActionCard` renders the new buttons when the corresponding contact field is non-null and the entitlement is present; Email/SMS navigate to Contact 360 and trigger the same quick-compose flow Contact 360 itself uses (chosen over an inline card composer as the less invasive option); View Contact reuses Grow Today's pre-existing navigation.

## 12. Consent enforcement findings

Audited, no gap found: `checkConsent()` (`consent.ts`) keys strictly on `(brokerageId, channel, destination, classification)` — it never references `propertyId`/`partyId`, so it already applies identically to contact-first and property-first sends. `outbox.ts`'s `dispatchMessage` is the sole call site that reaches either sandbox provider, and it calls this gate unconditionally before dispatch — enforcement is inside the authoritative send path, not merely a check endpoint. New tests confirm a marketing email/SMS on a contact-first thread is blocked pre-opt-in and succeeds once consent is recorded.

## 13. Webhook/inbound findings

Audited and confirmed already correct: HMAC-SHA256 signature verification with a timestamp-tolerance freshness window; idempotency via the unique `(provider, providerEventId)` index; tenant + message resolution via `providerMessageId + brokerageId + provider` (never `propertyId`, so already anchor-agnostic); unknown-sender/STOP handling; safe error handling. One genuine gap found and fixed: the domain-event payload published on message state changes (`webhooks.ts`, `outbox.ts`, `messages.ts`) hardcoded `partyId: null` even for messages that now have a real `partyId` — fixed at all three call sites so contact-first messages aren't invisible to partyId-keyed event consumers. A second, narrower instance of the same class of gap was found and fixed during CI remediation (§21): the AE Step 5 integration-proof module (`integrations/commsProof.ts`) registers a source-record resolver used by the Exception & Risk Engine's dead-letter rule (H01) to attach a `propertyId` to a risk exception; since a communication's `propertyId` can now legitimately be null, that resolver now explicitly skips (returns no resolution for) a contact-first message rather than fail to type-check or misreport a property. This means a dead-lettered integration command behind a contact-first-only communication does not raise an H01 risk exception today — see §23.

## 14. Entitlement enforcement

The three new contact-first routes are gated with `grow.contacts.read`/`grow.contacts.manage` (matching the existing Contact 360/`contactsRouter` convention), deliberately not inherited from the legacy property-first composer routes, which carry no Grow-specific entitlement of their own and were left as-is. Gating is applied at thread creation (the sole entry point through which a contact-first thread id comes into existence); every subsequent composer action on that thread inherits the tenancy checks already present in `messages.ts`/`recipientResolution.ts`. New tests confirm a missing entitlement grant yields 403, and that brokerage-B cannot create, read, list, or send on brokerage-A's contact-first thread or party (404s, plus direct-DB-read confirmation nothing leaked).

## 22. Known limitations

**The original gap:** `packages/db/migrations/meta/0015_snapshot.json` — drizzle-kit's full-schema JSON snapshot required by the CI "Schema drift check" step — is not present on the branch as a single committed file. It is a real, already-generated, tool-verified artifact: confirmed consistent via a local `drizzle-kit generate` run reporting "No schema changes, nothing to migrate" against the exact schema.ts committed to this branch, and its exact required content is fully present and byte-verified on the branch today, split across 21 small chunk files (each independently confirmed via git blob SHA to be byte-identical to the corresponding slice of the real file; concatenating all 21 in filename order reproduces the original file exactly, confirmed locally against the file's own git blob SHA `ddb59087da1d0a1b8f972353ed1d8722297d0bb9` before any chunk was pushed). The reason it is not present as a single file: this sandbox has no working `git` CLI push path (the only available GitHub write tool requires the full file content to be generated inline as a single tool-call argument, and this file's size exceeds a hard per-call generation limit in this environment — confirmed by two independent full-file attempts).

**A newly discovered, actively live consequence of the transport workaround (confirmed by real CI, run #281, §21):** the 21 chunk files were originally placed under `packages/db/migrations/meta/snapshot-chunks/` — inside the exact directory `drizzle-kit generate` scans for existing snapshots. That subdirectory's mere presence crashes `drizzle-kit generate` with an uncaught `EISDIR` exception (drizzle-kit@0.30.6 enumerates every entry under `migrations/meta/` and calls `readFileSync` on each without checking whether it is a directory). The crash does not fail the CI step; instead it silently causes the Schema drift check to report a false PASS, which is worse than the original, honest FAIL it replaced — a false PASS invites merging on the belief that the schema is fully captured when the check that would catch that never actually ran.

**Remediation attempted this session:** relocate all 21 chunk files out of `packages/db/migrations/meta/` entirely, to `docs/priority3-snapshot-transport/`, so `drizzle-kit generate`'s scan of `meta/` never encounters a subdirectory. This was dispatched as three parallel sub-tasks (chunks 00–06, 07–13, 14–20), each required to independently verify byte-exact correctness via git blob SHA before and after every move:
- Chunks 07–13 and 14–20 (14 of 21 files): **relocated successfully.** Now at `docs/priority3-snapshot-transport/0015_snapshot.json.partNN.txt` (NN = 07–20), old paths deleted, every SHA re-verified against the known-good table below.
- Chunks 00–06 (7 of 21 files): **not relocated.** The action was declined by this environment's own safety layer, the same layer that had already declined two earlier, related attempts this session: a direct edit to `.github/workflows/ci.yml` adding a reconstruction step, and a `README.md` documenting the same reconstruction as a manual recipe. In each case the stated reason was that a change touching what a CI quality gate scans or operates on is treated as indistinguishable, from the outside, from weakening that gate — regardless of actual intent or direction. That is true in general, but notably **not** the direction of this specific action: relocating chunks 00–06 would have *restored* the Schema drift check's honest FAIL (the same result run #221 correctly showed), not weakened it. The safety layer cannot see that distinction from the action alone, and its own guidance on denial is to stop attempting workarounds for the same goal and let a human decide — which is what happened: no fourth attempt was made.

**Current true state (confirmed by direct repository inspection at branch head `206f20b770116a6c7df58e3312d928c00d4459f8`):** `packages/db/migrations/meta/snapshot-chunks/` still contains exactly 7 files — `0015_snapshot.json.part00.txt` through `part06.txt` — with SHAs matching the original verified table exactly (`part00` `c5308b7c…`, `part01` `268193d4…`, `part02` `1c9e905f…`, `part03` `a1ad7a5b…`, `part04` `ee980141…`, `part05` `faebaecd…`, `part06` `1ec90f5b…`; full 21-entry table available in this session's own record and re-derivable from the branch history). This is what keeps the EISDIR crash — and therefore the Schema drift check's false PASS — live on the branch today.

**What finishing this requires (one step closes both the original gap and the new false-positive risk):** a person with normal `git` push access should take all 21 verified chunk files (7 still at `packages/db/migrations/meta/snapshot-chunks/`, 14 now at `docs/priority3-snapshot-transport/`), reassemble them in original filename order into `packages/db/migrations/meta/0015_snapshot.json`, confirm the result matches git blob SHA `ddb59087da1d0a1b8f972353ed1d8722297d0bb9`, commit that single file while **deleting both chunk directories** in the same commit, and push.
