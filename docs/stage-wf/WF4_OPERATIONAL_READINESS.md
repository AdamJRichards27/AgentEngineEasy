## 1. Objective

Make the Workflow Automation Engine observable, recoverable, and safely
operable before it is relied upon by the Run Transaction Vertical Slice.
This is explicitly **an operational-hardening phase, not a workflow
expansion phase**: it adds zero new triggers, zero new registered actions,
and zero new business workflows. Everything here answers one question —
when an execution or action gets stuck, fails, or needs a human decision,
can an operator see it, understand why, and safely act on it, without
touching the database by hand?

## 2. What this stage adds, and what it deliberately reuses unchanged

Reused unchanged: the entire evaluate/execute loop's shape
(`evaluateAndExecuteRule`, `executeAutomationAction`), the AI Governance
pipeline (`policyEngine.ts`, `actionRequests.ts`, `executionGateway.ts`),
`rules.ts`'s versioning and `setAutomationRuleStatus`, and the existing
3-role auth model (`requireAuth`/`requireRole`,
`apps/api/src/middlewares/auth.ts`). No parallel infrastructure was built:
this stage extends the existing `automationExecutions`/`automationActions`
tables with additive, nullable columns rather than introducing a second
job-tracking system, and reuses the existing compare-and-set claiming
convention `executionGateway.ts` already established
(`UPDATE ... WHERE status = X`) rather than inventing a new locking
mechanism.

New in this stage:

## 4. Schema changes

`packages/db/migrations/0002_clammy_molecule_man.sql` — 19 `ALTER TABLE ...
ADD COLUMN` statements (all nullable, all additive, zero risk to existing
rows) plus 4 new foreign-key constraints, generated by `drizzle-kit
generate` and verified against the live database (`drizzle-kit check` →
"Everything's fine"; a re-`generate` afterwards produced "No schema changes,
nothing to migrate"). `status` on both `automationExecutions` and
`automationActions` remains a plain, un-enumerated `text()` column, so the
three new status literals below required no DB-level enum migration at all.

New columns, identical set on both tables except where noted:

| Column | Purpose |
| --- | --- |
| `statusReason` (`automationExecutions` only) | Human-readable reason for the execution's current status — skip reason, block reason, cancel reason. |
| `lastFailureClassification` | The most recent `FailureClassification` seen among an execution's actions (execution row) or an action's own classification (action row). |
| `nextRetryEligibleAt` | When a `RETRY_SCHEDULED` row becomes claimable again. |
| `claimedAt` / `claimedBy` | Who/what last claimed this row for retry or recovery, and when — diagnostic, not itself a lock. |
| `cancelledAt` / `cancelledByUserId` | Who cancelled this row and when. |
| `resolutionNote` / `resolvedByUserId` / `resolvedAt` | An operator's free-text note and who/when it was added — available regardless of status, never itself a status transition. |

New status literals (plain strings, no migration needed): `RETRY_SCHEDULED`,
`FAILED_TERMINAL`, `CANCELLED` — extending the existing
`PENDING`/`RUNNING`/`SUCCEEDED`/`FAILED`/`BLOCKED`/`AWAITING_APPROVAL`
vocabulary. A legacy `FAILED` row from before this stage is still handled
correctly (§5) rather than silently orphaned.

## 5. Failure classification and retry policy

`operations.ts`'s `classifyActionFailure` is now the **sole** place that
decides whether a failure is retryable, replacing the old
`engine.ts`-local `NON_RETRYABLE_ERROR_PATTERN` regex (deleted). It maps an
action's `authorityDecision` + `errorMessage` to one of four classes:

- `RETRYABLE` — the default. Anything not matched by the two patterns below
  falls here deliberately: capping the blast radius through bounded
  attempts + backoff is safer than guessing a new failure string is
  terminal and silently giving up on something that was only a momentary
  blip.
- `VALIDATION_OR_POLICY` — tamper/policy-denial patterns
  (`PAYLOAD_TAMPERED`, `POLICY_DENIED`, `BLOCK_POLICY_CONFLICT`,
  `BLOCK_MISSING_ENTITLEMENT`, `BLOCK_MISSING_CONTEXT`, an unregistered
  action). Never retried, ever — retrying a tamper/policy denial would
  silently defeat the authority check that produced it.
- `TERMINAL_TECHNICAL` — clearly non-transient, investigation-required
  technical failures (a resource that no longer exists, a programming
  error). Deliberately narrow.
- `APPROVAL_REQUIRED` — reserved for a future distinction; not currently
  produced by any code path.

`computeBackoff` is deterministic exponential backoff with no jitter (base
30s, factor 2×, capped at 1h), so an operator can always predict exactly
when a `RETRY_SCHEDULED` row becomes eligible again from its `attemptCount`
alone.

`finalizeFailedAction` is called by `engine.ts` immediately after a genuine
execution-time failure (a policy denial already short-circuits to `BLOCKED`
before this is ever reached): it classifies the failure, and — if
`RETRYABLE` and attempts remain — writes `RETRY_SCHEDULED` with the
computed `nextRetryEligibleAt`; otherwise writes `FAILED_TERMINAL`. It never
inserts a new row — retries always reuse the same `automationActions` row,
the same convention the Foundation stage established.

## 6. Atomic retry claiming — the "never touch a refused row" guarantee

`claimActionForRetry` is the single gate both `engine.ts`'s
`retryAutomationAction` and any future ops-initiated retry go through. It
re-derives the row's classification (covering a legacy pre-classification
`FAILED` row that was never run through `finalizeFailedAction`) **before**
attempting the claim, so a `VALIDATION_OR_POLICY` row is rejected without a
single write — the row's `status`/`attemptCount` are provably untouched by
a refused retry, exactly as `engine.test.ts`'s "non-retryable failure"
scenario asserts. Only once eligibility is confirmed does it perform the
actual claim as a conditional `UPDATE ... WHERE status = <the status just
read>`, mirroring `executionGateway.ts`'s existing claim pattern: two
concurrent callers (a double-clicked operator retry, or a future worker
racing an operator) can both pass the eligibility read, but only one
`UPDATE` can ever affect the row — the loser is told `LOST_CLAIM_RACE`, it
never double-executes.

## 7. Execution rollup — one function, two callers, no possible drift

`recomputeExecutionRollup` (in `engine.ts`) re-queries **all** of an
execution's current `automationActions` rows fresh from the database and
writes `status`/`statusReason`/`lastFailureClassification`/
`nextRetryEligibleAt`/`completedAt` in exactly one place. It is called by
both the initial rule-evaluation path (`evaluateAndExecuteRule`) and the
retry path (`retryAutomationAction`) — the two code paths that can change
an execution's outcome can therefore never compute a different rollup for
the same execution, because they are the same code path.
`deriveExecutionRollup`/`deriveExecutionRollupExtras` (`operations.ts`) do
the actual derivation from a set of action outcomes; `ActionRollupOutcome`
now covers all six terminal-or-waiting action states, including the new
`CANCELLED`, so a cancelled action is never silently miscounted as absent
from the rollup.

## 8. Cancellation, resolution notes, and rule pause/resume

**Cancellation** (`cancelAction`/`cancelExecution`) is only permitted while
no irreversible side effect has occurred. "Irreversible" is defined
precisely: the linked `aiActionRequests` row (if any) has reached
`EXECUTING` or `COMPLETED` — `executionGateway.ts`'s own claim already
guarantees `execute()` runs at most once, so checking the linked request's
status is sufficient to know whether real work may already be underway.
Cancelling an execution also cancels its still-cancellable actions
(`PENDING`/`AWAITING_APPROVAL`/`RETRY_SCHEDULED`/`FAILED`), never actions
already past that point.

**Resolution notes** (`addExecutionResolutionNote`) are available
regardless of an execution's status and never themselves change status —
they exist purely so an operator's investigation is recorded even when no
state transition is warranted (e.g. "investigated, working as intended").

**Rule pause/resume** (`pauseAutomationRule`/`resumeAutomationRule`) add
only the audit/event trail an operator control requires on top of the
existing, unmodified `automationRules.status` column and
`rules.ts`'s`setAutomationRuleStatus` — there is deliberately no second
enable/disable mechanism.

## 9. Operational visibility — the ops API surface

`apps/api/src/routes/automationOps.ts`, mounted at `/api/automation/ops`,
gated `requireAuth` + `requireRole("Brokerage Administrator")` on every
route, tenant-scoped via `authedUser.brokerageId` on every query:

| Method & path | Purpose |
| --- | --- |
| `GET /health` | Structured health report — see the runbook for what `degraded` means. |
| `GET /executions` | Paginated, filtered list (`status`, `ruleId`, `correlationId`, `executionId`, `propertyId`, `transactionId`, `limit`/`offset`), newest first. |
| `GET /executions/:id` | Full detail: the execution, its triggering event summary, and every action row (redacted). |
| `POST /actions/:id/retry` | Claims and re-runs one action through the exact same `claimActionForRetry` gate described in §6. |
| `POST /executions/:id/cancel`, `POST /actions/:id/cancel` | `{ reason }` — see §8. |
| `POST /executions/:id/notes` | `{ note }` — see §8. |
| `POST /rules/:id/pause`, `POST /rules/:id/resume` | `{ reason }` — see §8. |

Every list/detail response is built through `operations.ts`'s own
`redactSensitiveFields`/`detailActionForOps` — there remains exactly one
place in the codebase deciding what is safe to show an operator, never a
second, route-local redaction. `redactSensitiveFields` allow-lists by
scanning keys against a pattern covering
token/secret/password/SSN/passport/credit-card/bank/IBAN/licence-number/
Medicare fields, and truncates any free-text field over 2000 characters.

## 10. Abandoned-`RUNNING` recovery and health reporting

`recoverAbandonedRunning` reconciles `RUNNING` action rows whose
`startedAt` is older than a threshold (15 minutes by default): if the
linked `aiActionRequests` row shows `COMPLETED`, the action is marked
`SUCCEEDED` after the fact; if it shows `FAILED`, the normal
`finalizeFailedAction` classification runs; otherwise the row is marked
`FAILED_TERMINAL` for manual investigation rather than guessed at or
silently re-executed. **This function is not currently invoked by anything
in this codebase** — no scheduler exists to call it periodically (§12).

`getAutomationHealth` reports `staleRunningActions`, `retryBacklog`,
`terminalFailuresLast24h`, and `approvalBacklog` via cheap aggregate
queries. `healthy: false` is reserved for a genuinely unreachable database;
a nonzero backlog degrades (`degraded: true`) but does not fail health,
because this repository has no worker to drain `RETRY_SCHEDULED` rows
automatically yet — a backlog is an expected operating state to surface,
not an outage.

New triggers, new registered actions, new business workflows, a
scheduler/worker process, a metrics backend integration (Prometheus/

## 12. Deferred dependencies — genuine gaps, not fabricated capabilities

- **No scheduler or worker process exists in this codebase.** Nothing
  automatically retries a `RETRY_SCHEDULED` row past its
  `nextRetryEligibleAt`, and nothing periodically calls
  `recoverAbandonedRunning`. Both are safe to run on demand today (via a
  future ops route or a manually-triggered job) — the durable, correct
  record they need already exists; only the periodic trigger is missing.
- **No metrics backend integration.** `getAutomationHealth`'s aggregate
  queries are the entire current visibility surface; wiring them into a
  real metrics platform is a documented, deferred integration point, not
  built here.
- **No dedicated admin UI.** The ops API surface is complete; a frontend
  page consuming it is out of scope for this stage.

## 13. How to extend this safely

1. A new failure pattern belongs in `operations.ts`'s
   `classifyActionFailure` — never re-implemented locally in `engine.ts` or
   in a route handler.
2. A new ops capability (a new query filter, a new mutation) should call
   into a new or existing `operations.ts` function, never query/mutate
   `automationExecutions`/`automationActions` directly from
   `automationOps.ts` for anything beyond the two existing read-model
   queries (`GET /executions`, `GET /executions/:id`).
3. A future scheduler/worker should call `claimActionForRetry`/
   `recoverAbandonedRunning` exactly as an operator-triggered route does —
   never a second, parallel claiming mechanism.
4. Never add a status transition to `addExecutionResolutionNote` — notes
   are deliberately status-independent.
